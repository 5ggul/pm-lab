# 공항나우 다음 고도화 준비안

작성: 2026-09-07. 범위: 첨부 진단 두 건과 현재 소스를 대조한 실행 준비 문서. 이 문서 작성으로 서비스 코드, 수집 주기, 색인 설정을 변경하지 않았다.

## 판단

방향은 맞다. 공항별 현재 데이터에 비교 기준과 다음 확인 행동을 연결하는 것이 핵심이다. 다만 지난 버전의 결함, 아직 없는 기능, 검색·광고 효과에 대한 추정이 섞여 있다. 첫 작업은 오래된 기상 숫자 차단이며, 비교 통계를 만들기 위한 관측 설계는 동시에 준비한다.

현재 확인: 9월 7일 14:47 KST API에서 cloudflare-cron-10m, ON_TIME, 출발·도착 모두 최신인 공항 15/15. 네이티브 관측 시작은 같은 날 13:21 KST다. 이 확인은 짧은 시점 점검이며 72시간 또는 7일 안정성 통과가 아니다.

## 스프린트 1 — 오래된 기상 차단과 사용자 동선

### AN-01: 기상 표시를 관측시각으로 통일 (P0)

대상: site.js의 setupSnapshotFreshness, applyWeatherToDetail, hydrateLiveWeather, 공항 목록·상세 템플릿.

- 현재 기상 기준을 관측 후 90분으로 통일한다. 서버의 90분 필터와 다른 프론트 180분 기본값을 정리한다.
- 처음부터 과거 샘플 숫자를 현재 화면의 기본값으로 렌더하지 않는다. 기본 HTML은 설명·출처·확인 방법과 숫자 없는 상태를 제공한다.
- API 실패 시 같은 공항의 직전 정상 관측이 90분 이내인 경우만 시각과 갱신 실패를 함께 표시한다. 초과·잘못된 시각·미래 시각은 숫자를 비운다.
- 응답 성공도 관측 최신성의 증거로 간주하지 않는다. 최신 필드가 null이면 예전 기온·기압 필드를 남기지 않는다.
- 탭 복귀, 장시간 열린 화면, 재요청 실패에도 만료 처리가 작동한다.
- JS가 꺼져 있어도 사흘 전 샘플 숫자가 보이지 않는다. 정적 과거 자료를 제공한다면 별도 명확한 과거 자료 영역으로 분리한다.

완료 기준: 90분 경계, 시간 파싱 실패, 미래 관측, 빈 응답, 타임아웃, 일부 null 필드, 탭 복귀, JS OFF 검증. 홈·목록·인천·일반 공항 상세 모두 확인. 운항 30분 보호는 유지.

### AN-02: 도구를 실제 항공편과 연결 (P1)

첫 대상은 인천 도착편 → 마중 계산기. 다음은 항공편 → 지연시간 계산기.

- 편명만으로 값을 넘기지 않고 운항일·방향·실제 운항편 ID를 함께 사용한다.
- URL에는 식별자만 전달하고 최신 데이터를 다시 조회한다. URL에 저장된 예상시각을 현재값으로 믿지 않는다.
- 공동운항 별칭 검색, 날짜가 다른 동일 편명, 자정 넘김, 예상시각 없음, 갱신 지연 상태를 처리한다.
- 사용자 여유시간은 수동 선택을 유지한다. T1/T2 선택으로 근거 없는 평균 입국시간을 자동 생성하지 않는다.
- 조회값·직접 입력값을 화면에서 구분하고, 공식 안내와 터미널 확인 링크를 제공한다.
- '지연됐으니 늦게 출발해도 된다'거나 탑승을 보장하는 문구는 사용하지 않는다.

완료 기준: 도착편 선택부터 결과까지 모바일 동선 연결, 입력 가정·예외·계산 예시·FAQ 제공, stale 값 자동 적용 금지.

### AN-03: 수집 상태 페이지 (P1)

/api/status를 바탕으로 /status/를 만든다. 소스별 마지막 시도·성공·지연 여부, 운항 30분/기상 90분 기준, 72시간·7일 관측 기간의 완료 여부를 보여준다. 일반 사용자에게 필요한 상태를 먼저 보여주고 원시 오류 코드는 부가 설명으로 둔다. noindex 유지. 현재 관측 구간 100%를 7일 가동률 100%로 표현하지 않는다.

## 스프린트 2 — 비교 통계 기반 수집

지금부터 설계·수집 연결을 시작한다. 28일 기다린 뒤 설계를 시작하지 않는다. 비교 표본이 충분해지기 전에는 수치를 만들어 넣지 않는다.

### AN-04: 지표 정의와 관측 계약 (선행 필수)

현재 소스상 주의점:

- airport-summary는 오늘 수집된 편들의 현재 상태 개수다. 시간대 지연률이나 확정 정시성 지표가 아니다.
- stats/queries.js의 airportCurrent는 당일 전체를 조회하고 baseline은 특정 시각 집계를 조회한다. 그대로 연결하면 분모 범위가 달라진다.
- aggregation.sql은 최신 flight_current의 상태를 사용한다. DELAYED에서 DEPARTED/ARRIVED로 바뀐 편을 단순 상태 집계로 확정 지연 이력에 포함할 수 없다.
- 평균 지연시간 초안은 전체 delay_minutes 합을 DELAYED 상태 건수로 나누므로 대상 일치 검증이 필요하다.
- 이벤트 수는 항공편 표본수가 아니다. 동일 편의 이벤트 열 건은 항공편 한 편이다.

제안하는 1차 제품 지표는 '동일 관측시점의 지연 상태 비중'이다. 확정 정시성은 별도 후속 지표로 둔다.

1. 공항·방향·예정시각 KST 한 시간 구간·관측 컷오프를 키로 정한다.
2. 현재와 과거 모두 같은 예정시각 구간과 같은 상대 관측시점에서 상태를 집계한다. 과거의 최종 상태를 현재 중간 상태와 비교하지 않는다.
3. UNKNOWN은 분모에서 제외하고 별도 건수·비율을 표시한다. 결항은 별도 분자이며, 지연 비중의 분모에 포함하는지 명시한다. 1차는 기존 알려진 상태 분모를 유지하되 제목을 '지연 상태 비중'으로 제한한다.
4. 원본상 출발/도착 완료와 실제 시각의 확보율을 별도로 측정한다. 예상시각을 실제 시각으로 승격하지 않는다.
5. 같은 공항의 제공기관 소유 범위와 공동운항 중복 제거를 기존 규칙대로 유지한다.

예시 UI는 숫자를 채우지 않고 다음 계약으로 준비한다:

- 현재: 분자/분모, 관측 기준시각, UNKNOWN, 결항, 방향, 예정시간 구간.
- 과거: 최근 28일 같은 요일·같은 시간/관측 컷오프의 분자 합 ÷ 분모 합. 일별 비율 단순 평균과 혼용하지 않는다.
- 차이: %p, 비교 날짜 수, 기준 표본수, 수집 커버리지.
- 불충분: '비교 이력을 쌓고 있습니다' 또는 구체적 누락 사유.

### AN-05: 관측 집계 저장과 재실행

- 의미 있는 항공편 변화만 flight_events에 저장하는 원칙은 유지한다.
- 별도의 정해진 관측 버킷에 집계·품질 정보를 저장한다. 운항 이벤트 기록과 주기적인 통계 관측은 역할이 다르다.
- 제안 필드: metric_version, 공항, 방향, service_date, 예정 hour_kst, 관측 버킷, 실제 관측·공개 시각, source_run_id, known/unknown/delayed/cancelled 건수, completeness, freshness.
- 전체 정상 수집 완료 이후에만 집계한다. 실패·부분 수집 버킷을 0편 또는 정시로 기록하지 않는다.
- 동일 버킷 재시도는 멱등적으로 처리한다. 제공기관 혼합이나 날짜 경계가 바뀌지 않도록 테스트한다.
- 과거 이벤트와 수집 성공 기록으로 정확하게 복원 가능한 구간만 재집계한다. 자료 없는 기간은 채우지 않는다.
- 원시 이력 보존·집계 보존·D1 쓰기량을 실제 용량과 함께 산정한 뒤 스케줄에 연결한다.

비교 공개 게이트 제안: 최소 현재 20편, 과거 20편, 서로 다른 과거 동일 요일 4회, 각 대상 관측 구간의 충분한 수집 커버리지. 20편은 서비스의 보수적 최소선이며 통계적 유의성 보장이 아니다. 임의의 ±1%p만으로 유의미한 상승을 선언하지 않는다. 컷오프·분모·결항 포함 여부를 방법론과 테스트에서 동일하게 고정한다.

## 다음 단계와 보류 범위

- 인천 주차·출국장 혼잡은 공식 API 문서, 키 사용 권한, 갱신 주기, T1/T2 구분, 누락·운영시간 필드를 먼저 검증한다. 아직 API 가용성을 검증하지 않았으므로 연결 완료나 대기시간 예측을 약속하지 않는다.
- 노선 지연률·편명 정시성·CSV/Dataset은 관측 품질과 실제 시각 확보율을 확인한 뒤 만든다. 편명 하나가 노선 변경 전후를 섞지 않게 한다.
- 공항별 /weather/, /delay/, /arrivals/ URL을 일괄 생성하지 않는다. 독립 데이터와 독립 사용 목적이 충분할 때만 분리한다.
- 가이드 편수 자체를 KPI로 삼지 않는다. 도구 사용 완료율, 공식 안내 연결, 재방문, 자료 오류율을 함께 본다.
- 검색 효과는 최종 도메인·선택적 색인 후 검색도구 실측으로 판단한다. 특별한 AEO 스키마나 AI 인용 보장은 주장하지 않는다.
- data-nosnippet은 급변 숫자 영역에 제한 적용을 검토한다. 전체 설명·방법론까지 막지 않으며 모든 검색엔진의 동일 동작을 가정하지 않는다.
- noindex 해제, 최종 도메인, AdSense 신청은 이번 준비 범위 밖이다. 기존 수집은 유지한다.
